# Connected account and balance persistence

Issue #21 finishes the R1.1 connected persistence path by aligning `LedgerApiAccountRepository` and `LedgerApiBalanceSnapshotRepository` with the backend OpenAPI v1 contract exactly: list, create, and retrieve for banks, accounts, and balance snapshots, each create mutation carrying a fresh `Idempotency-Key`, and RFC 7807 `application/problem+json` failure bodies parsed into a typed error taxonomy (`src/domain/errors/LedgerRequestErrors.ts`). Traceability: FR-002, FR-009, FR-010, FR-011, FR-012, NFR-003.

The `AccountRepository` port dropped `update` and `delete` rather than stubbing them: the contract defines neither operation, `delete` had no consumer, and the single `update` caller (the transaction-import flow's optional `lastTransactionDate` convenience write) already records the authoritative observation through the balance-snapshot repository, so the removal is compile-time-enforced contract compliance instead of a runtime-rejected dead code path. A getter (`findById`, `findBankById`) resolves to `null` only when the backend returns 404 for the requested resource; every other status maps to a thrown `LedgerRequestErrors` subclass, so a transient or authorization failure is never confused with "does not exist." Idempotency-key generation (`src/infrastructure/api/idempotency.ts`, `crypto.randomUUID()` per invocation) lives in infrastructure, not on the domain ports, because retries of a logical operation are not yet orchestrated by the application layer — a per-invocation key is the contract-satisfying minimum without leaking a transport concern into a domain signature.

`useAccountRepository` and `useBalanceSnapshotRepository` return the live API repository only when `VITE_LEDGER_API_BASE_URL` is configured; otherwise they return `UnavailableAccountRepository`/`UnavailableBalanceSnapshotRepository`, which reject every operation with `LedgerRepositoryConfigurationError`. The former `LocalStorageAccountRepository`, `LocalStorageBalanceSnapshotRepository`, and `LocalStorageBalanceSnapshotStore` were removed rather than kept as a fallback, and the dashboard renders explicit loading and retryable-failed states instead of ever presenting a failure as an empty account list. Local storage remains legitimately in use elsewhere in this codebase only for the last-active tenant preference (`LocalStoragePreferenceRepository`, revalidated against backend membership on every load) and for the obligations, budgets, and transactions repositories, which are out of scope for this change and remain pending their own connected slices.
