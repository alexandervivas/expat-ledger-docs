| [FR-011](FR-011-multi-currency-balances.md)               | Multi-Currency     | [ADR-005](/reference/backend/decisions/ADR-005-bank-and-balances.md); [ADR-021](/reference/backend/decisions/ADR-021-account-balance-contract-ownership.md); [ADR-022](/reference/backend/decisions/ADR-022-authenticated-active-tenant-selection.md); [ADR-023](/reference/backend/decisions/ADR-023-cross-service-integration-test-harness.md); [ADR-025](/reference/backend/decisions/ADR-025-statement-import-draft-lifecycle.md)     | Dual currency reporting. Exact-decimal money and source-aware balance snapshot contract (issue 64); FX conversion behavior unchanged. `balance_snapshots.balance_amount` widened to unconstrained `NUMERIC` so persistence no longer imposes a stricter scale than the domain `Money`/`Amount` type produces. The shared-kernel `Amount.setScale(2, HALF_UP)` gap against the contract's arbitrary-precision claim is a governed cross-cutting ADR-021 gap, unchanged by issues 60 and 62; it requires a separately approved ADR and implementation owner. Issue 62's public gRPC reads preserve the authorized snapshot's decimal-string money, source/semantics, UTC `recorded_at`, and exact PostgreSQL-representable microsecond as-of timestamps; non-zero sub-microsecond input is rejected rather than rounded. Issue 65 narrows public creation to `MANUAL`/`OBSERVED` with timestamp-as-of while preserving exact decimal strings and UTC precision through the gateway. Issue 66 proves no layer beyond the documented domain normalization loses precision: amounts at the domain scale, including negatives, round-trip exactly through HTTP, reload, and the raw SQL column, and a higher-scale submission is shown to be deterministically HALF_UP-normalized rather than truncated or floating-point-corrupted. The `Amount.setScale(2, HALF_UP)` scale question itself is now tracked as its own issue (#84) with the ADR requirement recorded there. Issue 79 types the statement reconciliation difference as a required, never-null exact decimal `Money` value — `(opening + bookedNetChange) - closing`, `"0.00"` when `RECONCILED` and the exact signed non-zero decimal when `NEEDS_REVIEW` — with all four monetary values sharing the account's native currency and no floating-point representation anywhere in the new shapes. The `Amount.setScale(2, HALF_UP)` constraint (#84) is cross-referenced from ADR-025 as an open constraint; the contract deliberately keeps its exact-decimal claim and must be resolved before importing a currency with a different minor unit. Issue 82 implements that contract claim in Scala: all reconciliation arithmetic runs through the shared-kernel `Money`/`Amount` `BigDecimal` types, opening/closing/net-change/difference must share one currency or evaluation fails with a typed `CurrencyMismatch` and produces no outcome, no currency is converted or inferred during reconciliation, and a mechanical test asserts no `Double`/`Float` appears in the code of any reconciliation source. Zero is detected with the existing `Money.isZero` (numeric equality on `scala.math.BigDecimal`, so `0` and `0.00` agree) and **no epsilon or tolerance band is used anywhere**. The `Amount.setScale(2, HALF_UP)` constraint (#84) is unchanged and still open: adding and subtracting scale-2 values is exact, so no rounding occurs at the delivered EUR scale, but a currency whose minor unit is not two digits must not be imported before #84 is resolved. Separately disclosed by issue 82's pre-commit review and **not** introduced by it: the contract's `Money.amount` is a decimal string whose pattern documents rejecting binary floating-point JSON numbers, while the shared-kernel `Amount` Circe codec encodes and decodes a JSON number. Nothing in issue 82 serializes anything, so the drift is unreachable there, but issue #83 cannot serialize `StatementReconciliation` to the contract with the derived codecs as they stand. Issue #83 also inherits an explicit constraint from issue 82: do not `deriveDecoder` a `StatementReconciliation` — decode its components and re-run `evaluate` so the reconciliation state is derived rather than trusted. |

## Documented Traceability Gaps

Recorded here rather than closed by inventing requirement identifiers.

- **Secret-management and cryptographic-assurance proportionality** (issue [#101](https://github.com/alexandervivas/expat-ledger-backend/issues/101), [ADR-027](/reference/backend/decisions/ADR-027-secret-management-proportionality.md), 2026-08-06). No FR/NFR mandates a particular secret-management technology, a declared assurance level, or the proportionality of either to the product's actual risk, users, and team size. The question was answered by ADR-027 as a documented decision with evidence; the requirement set still does not express it. Adjacent to **FR-008** (data encryption), **FR-007** (RBAC security), **NFR-001** (performance, via the ASVS 13.3.3 latency deferral), **NFR-004** (portability, via the retained `SecretManager` port), and **USP-007** (zero-knowledge ledger). ADR-027 additionally requires that a declared assurance level cite its standard and its evidence, and that documented posture does not count as aligned while the runtime contradicts it.
- **CI-level security verification** (ADR-026). No FR/NFR mandates dependency or secret scanning directly; the gates protect enforcement of FR-007, FR-008, and FR-012.
- **Index and query path for `accounts.account_number`**. FR-008's deterministic-encryption justification cites reconciliation and duplicate detection that have no index, unique constraint, or query behind them. Recorded by ADR-027 as needing its own issue.
